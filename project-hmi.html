控制中心改版迭代

当功能不断涌入，控制中心如何保持「伸手就到」？

我的角色 交互设计 · 面板架构与排序 · 交互规范
产品 某量产车机 · 控制中心
状态 已随量产版本上线

"驾驶中，找一个开关的每一秒都有成本。"

控制中心从屏幕顶部下拉呼出，覆盖在一切应用之上——亮度、音量、后备箱、遮阳帘，驾驶员行驶中最常伸手去够的开关都聚在这里。它同时也是系统的「泄洪区」：每当产品定义一个新功能而它没有明确归属时，控制中心往往是第一候选落点。我作为 UX 设计师深度参与控制中心的改版迭代与新功能承接：加什么功能是产品定义的；怎么进、放在哪、怎么呈现，是我定的。

问题：一级入口的结构性膨胀

车机功能沿版本持续增长——新的车身控制、场景模式、舒适性配置不断要求「上控制中心」。而面板的物理条件是刚性的：屏幕尺寸固定、驾驶中可安全触达的热区有限、单次瞥视时长有硬约束。功能是流量，面板是容器——没有准入和排序规则的容器，迟早溢出。

改版前的具体表现：开关、滑条、模式选择器混排在同一平面，视觉权重接近；全局高频控制（驾驶模式、灯光）与低频开关（油箱解锁、洗车模式）争夺同一层空间；新功能「来一个塞一个」，默认序没有系统化依据。

问题定义

在容器不变、功能持续增加的前提下，如何让驾驶员用最少的注意力找到并够到目标开关——并且让这个能力在未来版本的功能增长下仍然成立？一次性的整理谁都会做，可持续的规则才是设计产出。拆出三个变量：什么配进来（准入）、按什么排（排序）、装不下怎么办（容量）。

竞品拆解：五个维度看控制中心

改版前做过竞品布局对比；整理本案例时深化为五个维度的结构化拆解（全部基于公开渠道界面）：入口密度、常驻 vs 可自定义、开关状态可读性、驾驶中热区可达性、与设置页的层级分工。

两个关键输入

「系统钦定核心区 + 少量自定义」是主流折中——全靠用户自定义，大多数用户从不改；全系统钦定，重度用户不满。真正拉开差距的是开关状态可读性：做得好的用色彩 + 图标双通道编码，做得差的开与关只差一点透明度。

核心设计决策

四个决策分别回答「什么配进来、按什么排、装不下怎么办、细节怎么稳」，共同构成控制中心的守门逻辑。

01

架构：固定区与可编辑区

哪些内容配常驻第一屏、不许用户移走？

固定区（不可编辑，永远在第一屏）：桌面切换、亮度与音量、驾驶模式、灯光、HUD——要么是全局状态的「真相之源」，要么是驾驶中需要立即触达的控制。
可编辑区（网格开关，默认序 + 用户可编辑）：后备箱、油箱解锁、遮阳帘、洗车模式……所有「一步开关 / 一步档位」类功能。

进固定区的三条判据：驾驶中的即时性、状态的全局性、入口的不可替代性。固定区是稀缺资源，宁缺毋滥。

放弃

全部可编辑
把排序难题外包给用户，大多数用户从不配置；且全局控制被用户移走后没有兜底入口

放弃

按功能类别分组
驾驶中的任务是「调一个具体开关」而非「浏览一个类别」，分组徒增一次定位

02

排序：可编辑区的默认优先级

用户可以编辑，但绝大多数用户永远用默认序——默认序谁负责？

先按使用频率排出基础序 → 驾驶安全相关的操作局部上浮 → 落位遵循「从上到下、从左至右」的阅读与触达优先级：排位最高的功能，落在面板打开后视线和手指最先到达的位置。

默认序的责任外包不掉——自定义解决个体差异，解决不了默认体验。这份默认优先级是我主导的核心产出。

03

容量：上限与翻页

功能继续增长，第一屏终会装满——然后呢？

3.0 版本的回答不是「再挤一挤」，而是给容量立规则：

可编辑区横向翻页，超过一页出现页标；页数设上限（3 页）——上限不是技术限制，是设计立场：控制中心不是抽屉，装不下的功能应该回设置页，而不是无限加页。

上限倒逼准入：新功能要进来，讨论的不再是「挤哪」，而是「它配不配占用这有限的容量」。这一条把前两个决策从「一次整理」变成了「可持续的机制」。

04

细节：车规与多用户约束下的呈现

规则立住了，边界条件下还稳吗？

  • 手势冲突——面板以上拉或点空白收起，但亮度/音量滑条的拖动与上拉收起冲突：滑条区域不响应收起手势。宁可收起多一步，不让调亮度误触关面板
  • 主副驾双面板——副驾有独立控制中心，内容镜像右对齐（靠副驾手侧）；副驾面板上可呼出主驾面板，反之不可——主驾操作优先级更高
  • 盲操与瞥视——图标 + 状态色双通道编码；亮暗态下对比度分别校验

结果

改版随量产版本上线，3.0 的翻页与容量机制随后续版本上线。一个如实的观察：改版前后的界面乍看差别不大——这正是系统级迭代的特点。变化不在视觉，在规则：固定区/可编辑区架构、默认优先级、容量上限，让后续每一个新功能的承接都有据可依，膨胀不再靠一次次改版兜底。

延伸思考：当 Agent 能听懂「我有点冷」，控制中心还剩什么？

以上全部工作有一个隐含前提：用户自己动手操作。LLM 驱动的座舱 Agent 正在改变这个前提——当用户说「我有点冷」，Agent 直接调高温度，不需要任何人找任何开关。为「人找开关」而生的控制中心，是否就该消失？

我的判断：不是消失，而是转型——从操作入口变成 Agent 行为的可见层。Agent 接管执行后，控制中心的新职责恰恰是 Agent 无法自我提供的：

01

执行回显

Agent 刚才调了什么？温度从几度到几度？动作要被看见，信任才有依据。

02

当前状态

语音是瞬时的，状态需要一个常驻的、可一眼读取的真相之源。

03

一键撤销

Agent 理解错了（「我有点冷」其实是想关空调），撤销必须比重新对话快。

04

授权开关

哪些操作 Agent 可以直接做、哪些要先问我——授权边界需要一个用户可控的物理落点。

有趣的对称

手动面板成为人对 Agent 的信任兜底。固定区/可编辑区与默认排序的逻辑此时依然成立，只是对象变了——从「用户最常操作的功能」变成「用户最需要看见和干预的 Agent 行为」：高频被 Agent 代办的操作，其回显和撤销入口反而要排最前。

概念稿：控制中心作为 Agent 行为可见层（回显流 + 撤销 + 授权开关）· 图片占位

设计反思

这个项目里我做的最有价值的东西不是某一版界面，而是一套能持续运转的规则：固定与可编辑的架构、默认优先级、容量上限。界面会被下一次改版覆盖，规则会被下一个功能继续使用。

这也是我看待座舱 Agent 时代的方式：我做过 Agent 将要操作的工具层，所以我知道「可见、可撤销、可授权」不是锦上添花，而是控制中心存在的下一个理由。
