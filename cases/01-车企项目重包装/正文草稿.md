## 1. 背景与我的角色(1-2 页)

控制中心是车机里使用频率最高的面板之一:从屏幕顶部下拉呼出,以覆盖层出现在一切应用之上——亮度、音量、后备箱、洗车模式、遮阳帘,驾驶员行驶中最常伸手去够的开关都聚在这里。它同时也是系统的"泄洪区":每当产品定义一个新功能而它没有明确归属时,控制中心往往是第一候选落点。

我在该项目中作为 UX 设计师深度参与控制中心的改版迭代与新功能承接。分工上:**加什么功能是产品定义的;怎么进、放在哪、怎么呈现,是我定的。** 具体包括:

- 面板的整体架构:哪些内容固定常驻、哪些进可编辑区
- 可编辑区的默认优先级排序
- 新功能的进入方式与呈现形态(开关 / 滑条 / 档位选择器 / 场景卡片)
- 呼出收起手势、翻页机制、主副驾双面板等交互规范

同期我还负责主框架、Dock、蓝牙电话、浏览器等系统模块的交互设计(一句话带过,证工作面宽度)。

## 2. 问题:一级入口的结构性膨胀(2-3 页)

### 2.1 矛盾是结构性的

车机功能沿版本持续增长——新的车身控制、场景模式、舒适性配置不断要求"上控制中心"。而面板的物理条件是刚性的:屏幕尺寸固定、驾驶中可安全触达的热区有限、单次瞥视时长有硬约束。功能是流量,面板是容器——没有准入和排序规则的容器,迟早溢出。

具体表现(改版前):

- 开关类、滑条类、模式类控件混排在同一平面,视觉权重接近,找目标靠"逐个看"
- 全局高频控制(驾驶模式、灯光、HUD)与低频开关(油箱解锁、洗车模式)争夺同一层空间
- 可编辑能力有限,默认序没有系统化的排序依据,新功能"来一个塞一个"
- 【需素材:改版前一级可见控件数量级,以及有没有当时被诟病的具体例子】

### 2.2 用户怎么说

【需素材:用户反馈条目,脱敏引用 2-3 条;确认属于改版前抱怨还是上线后评价,决定放本节还是第 5 节】

### 2.3 问题定义

> **在容器不变、功能持续增加的前提下,如何让驾驶员在行驶中用最少的注意力找到并够到目标开关——并且让这个能力在未来版本的功能增长下仍然成立?**

后半句是这次改版真正的重点:一次性的整理谁都会做,**可持续的规则**才是设计产出。拆出三个可设计的变量:**什么配进来(准入)、按什么排(排序)、装不下怎么办(容量)**——对应第 4 节的三个决策。

## 4. 设计决策(5-7 页,核心章节)

### 决策 A|架构:固定区与可编辑区的划分

面板被划分为两类空间,这是整个改版最重要的一刀:

> **固定区**(不可编辑,永远在第一屏):桌面/视图切换、亮度与音量、驾驶模式、灯光、HUD——它们要么是全局状态的"真相之源",要么是驾驶中可能需要立即触达的控制。
> **可编辑区**(网格开关,默认序 + 用户可编辑):后备箱、油箱解锁、遮阳帘、洗车模式、车窗全开/全关……所有"一步开关/一步档位"类功能。

什么配进固定区的判断依据:

1. **驾驶中的即时性**——行驶中可能需要"现在、马上"操作(灯光、驾驶模式)
2. **状态的全局性**——不属于某个功能,而属于整台车的当前状态(亮度、音量、HUD)
3. **不可替代性**——没有其他稳定入口兜底

固定区是稀缺资源,宁缺毋滥:进固定区的功能【需校准:最终是几个】,其余一律走可编辑区——**"产品让加"由此转写成"我定义了它进哪一层、以什么形态出现"**。

**考虑过但放弃的方案**【需校准:是否真实考虑过;若否改写为推演式】:
- *全部可编辑*:把排序难题外包给用户,大多数用户从不配置,默认体验没人负责;且全局控制(亮度/驾驶模式)被用户移走后没有兜底入口
- *按功能类别分组*:驾驶中的任务是"调一个具体开关"而非"浏览一个类别",分组徒增一次定位

【配图 4:固定区/可编辑区架构图(改版前后对比)】

### 决策 B|排序:可编辑区的默认优先级

用户可以编辑,但**绝大多数用户永远用默认序**——默认序的责任外包不掉,这是我主导的核心产出。排序依据三个因子做三轮筛选:

> ⚠️【需校准:此框架为重构草案,必须与你的真实判断过程对齐,面试追问要能顺着讲】

1. **使用频率**——高频操作排前(基础序)
2. **驾驶安全相关性**——行驶中"必须立即完成"的操作局部上浮
3. **场景聚类**——同一使用场景中先后发生的操作相邻放置(如洗车模式与后视镜折叠)【需校准:当时是否有这层考虑,没有就删】

排序结果落在网格上遵循"从上到下、从左至右"的阅读与触达优先级——排位最高的功能落在面板打开后视线和手指最先到达的位置。

【配图 5:默认序示意(抽象化,不出现完整真实清单)+ 三因子作用标注】

### 决策 C|容量:上限与翻页,让膨胀有处可去(3.0)

功能继续增长,第一屏终会装满。3.0 版本的回答不是"再挤一挤",而是**给容量立规则**:

- **横向翻页**:超过一页时出现页标,可编辑区横向滑动翻页
- **容量上限**:页数设上限(3 页)——上限不是技术限制,是**设计立场**:控制中心不是抽屉,装不下的功能应该回设置页,而不是无限加页
- 上限倒逼准入:每次新功能要进来,讨论的不再是"挤哪",而是"它配不配占用这有限的容量"

这一条把决策 A/B 从"一次整理"变成了"可持续的机制"。

【配图 6:翻页机制 + 容量规则示意】

### 决策 D|细节:车规与多用户约束下的呈现(1-2 页)

- **手势冲突处理**:面板以"上拉或点空白收起",但亮度/音量滑条区域的拖动手势与上拉收起冲突——规则:滑条区域不响应收起手势,宁可让收起多一步,不让调亮度误触关面板(驾驶中误关面板的代价更高)
- **主副驾双面板**:副驾有独立控制中心,内容镜像为右对齐(靠副驾手侧);副驾面板上可呼出主驾面板,反之不可——主驾的操作优先级高于副驾
- **盲操与瞥视**:开关用图标+状态色双通道编码;**亮暗态**下对比度分别校验
- 【需校准:这四条哪些是你直接定的、哪些是配合落地的,词按实际情况定】

## 6. ✨ LLM 延伸:当 Agent 能听懂"我有点冷",控制中心还剩什么?(2 页)

> 本节是概念推演,不是已实施项目;与案例②(LLM 座舱 Agent 重设计)直接衔接。

### 6.1 问题

上面的全部工作有一个隐含前提:**用户自己动手操作**。排序、热区、容量,都是在优化"人找开关"的效率。但 LLM 驱动的座舱 Agent 正在改变这个前提——当用户说"我有点冷",Agent 直接调高温度,不需要任何人找任何开关。为"人找开关"而生的控制中心,是否就该消失?

### 6.2 判断:不是消失,而是转型——从操作入口变成 Agent 行为的可见层

1. **执行回显**——Agent 刚才调了什么?动作要被看见,信任才有依据
2. **当前状态**——语音是瞬时的,状态需要常驻的、可一眼读取的真相之源
3. **一键撤销**——Agent 理解错了,撤销必须比重新对话快
4. **授权开关**——哪些操作 Agent 可以直接做、哪些要先问我,需要一个用户可控的物理落点

**手动面板成为人对 Agent 的信任兜底。** 有趣的对称:固定区/可编辑区与默认排序的逻辑此时依然成立,只是对象变了——从"用户最常操作的功能"变成"用户最需要看见和干预的 Agent 行为"。高频被 Agent 代办的操作,其回显和撤销入口反而要排最前。

【配图 8:概念稿——控制中心作为 Agent 行为可见层】

### 6.3 通往案例②

可见层回答的是**呈现**;更难的问题是授权边界本身怎么设计——什么该问、什么可直接做、错了怎么降级。这是案例②用完整重设计和可运行 demo 回答的问题。

## 附录 A|面试追问预演(不进 PDF,自用)

**Q:排序的数据从哪来?有埋点吗?**
A 草案:【需校准:如实】频率判断来自用户反馈中被抱怨"难找"的功能、竞品头部共识、团队走查的交叉验证。框架设计成"分轮筛选"而不是加权打分——打分需要精确数据,筛选只需要序关系,这是数据条件有限时更诚实的方法。

**Q:固定区凭什么是这几个?产品要求把 X 放固定区怎么办?**
A 草案:三条判断依据(即时性/全局性/不可替代性)就是讨论的共同语言——"它是全局状态吗?驾驶中需要立即够到吗?"比"我觉得不该放"更容易达成一致。(⚠️ 不编冲突,如实为准)

**Q:页数上限为什么是 3?**
A 草案:【需校准:如实——若当时有推导讲推导】上限的具体数值不是重点,重点是"必须有上限"这个立场:无上限的可编辑区会变成第二个设置页,控制中心的"快"就没了。3 页在当时的功能池规模下够用且留有余量。

**Q:改版前后看起来差别不大,你的产出到底是什么?**
A 草案:产出是规则不是像素。固定/可编辑架构、默认序、容量上限——这些决定了之后每个新功能怎么进来。系统级设计的价值恰恰是"看起来没变,但再也不乱了"。

**Q:你是外包身份,决策真是你做的吗?**(若被问到)
A 口径:如实——需求定义在产品,方案层面的架构、排序、规范由我产出并通过评审。评审通过靠方案本身站得住。
