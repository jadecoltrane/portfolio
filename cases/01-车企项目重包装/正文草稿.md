## 1. 背景与我的角色(1-2 页)

控制中心是车机里使用频率最高的面板之一:空调、音量、屏幕亮度、蓝牙、座椅——驾驶员在行驶中最常伸手去够的开关都聚在这里。它同时也是系统的"泄洪区":每当产品定义一个新功能而它又没有明确归属时,控制中心往往是第一候选落点。

我在该项目中作为 UX 设计师深度参与控制中心的改版迭代与新功能承接。分工上:**加什么功能是产品定义的;怎么进、放在哪、怎么呈现,是我定的。** 具体包括:

- 一级入口的功能排序与布局
- 新功能的进入方式与呈现层级(常驻开关 / 可展开面板 / 沉入设置页)
- 开关状态的视觉可读性与驾驶场景约束的落地

同期我还负责主框架、Dock、蓝牙电话、浏览器等系统模块的交互设计【需校准:一句话如何措辞,证工作面宽度即可,不展开】。

## 2. 问题:一级入口的结构性膨胀(2-3 页)

### 2.1 矛盾是结构性的,不是某一次需求造成的

车机功能沿版本持续增长,而控制中心的物理条件是刚性的:屏幕尺寸固定、驾驶中可安全触达的热区有限、单次瞥视时长有硬约束。功能是流量,面板是容器——没有准入和排序规则的容器,迟早溢出。

改版前的具体表现:

- 一级入口数量【需素材:改版前多少个】,超出驾驶中可扫视定位的合理范围
- 高频功能与低频功能平铺混排,视觉权重接近,找目标靠"逐个看"
- 部分高频开关落在驾驶位难以触达的区域【需校准:是否属实,当时屏幕布局是横屏/竖屏?】

### 2.2 用户怎么说

【需素材:改版前的用户反馈条目,脱敏引用 2-3 条。示例格式:】

> "开个座椅加热要翻半天。" —— 来自【渠道类型】的用户反馈(脱敏转述)

【若反馈全部属于上线后评价,本节改为用走查/评审记录锚定问题,反馈移到第 5 节】

### 2.3 问题定义

把现象收敛成一句设计问题:

> **在容器不变、功能持续增加的前提下,如何让驾驶员在行驶中用最少的注意力找到并够到目标开关?**

这句话拆出三个可设计的变量:**什么配进来(准入)、按什么排(排序)、怎么被看见(呈现)**——对应第 4 节的三个决策。

## 3. 竞品拆解:五个维度看控制中心(2-3 页)

改版前我做过竞品布局对比;整理本案例时,我把它深化为五个维度的结构化拆解(全部基于公开渠道界面,详细分析见附录/竞品拆解文档):

| 维度 | 问的问题 |
|------|---------|
| 入口密度 | 一级放多少个?超过多少开始依赖搜索式扫视? |
| 常驻 vs 可自定义 | 谁替用户决定?系统钦定、用户自定义,还是混合? |
| 开关状态可读性 | 不点进去,能否一眼读出当前是开是关、档位多少? |
| 驾驶中热区可达性 | 高频开关是否落在驾驶位单手可达区? |
| 与设置页的层级分工 | 控制中心和设置页的边界在哪?重复出现还是严格分工? |

拆解得出的三个关键输入【需校准:与竞品拆解.md 核验后的结论对齐】:

1. 头部玩家普遍把一级入口控制在【N】个以内,超出部分用"更多/展开"收纳——**密度有共识上限**
2. "系统钦定 + 少量自定义"是主流折中:全靠用户自定义,大多数用户从不改;全系统钦定,重度用户不满
3. 开关状态可读性是拉开差距的地方:做得好的用色彩+图标双通道编码,做得差的开和关只差一点透明度

## 4. 设计决策(4-6 页,核心章节)

### 决策 A|排序逻辑:高频、安全相关、够得着的排前面

> ⚠️【需校准:以下框架是基于素材底账重构的草案。必须与你的真实判断过程对齐——面试追问时要能顺着讲。若当时的实际排法与此不同,以真实回忆为准改写。】

一级入口的排序依据三个因子:

1. **使用频率**——驾驶中高频操作(空调温度、音量、除雾)优先
2. **驾驶安全相关性**——行驶中"必须立即完成"的操作(除雾、雨刮相关)权重上浮,哪怕绝对频率不是最高
3. **热区可达性**——排序结果映射到布局:权重最高的功能放驾驶位单手可达热区,权重递减向远端排布

三个因子不是打分表,而是**三轮筛选**:先按频率排出基础序,再用安全相关性做局部上浮,最后按热区做布局映射。【需校准:当时是否有类似的分轮判断?】

**考虑过但放弃的方案**【需校准:是否真实考虑过;若否,改写为上线后推演,见素材清单第 3 条】:

- *按功能类别分组*(空调一组、多媒体一组):结构清晰,但驾驶中的任务是"调一个具体开关"而非"浏览一个类别",分组徒增一次定位;且各组内高低频混排,热区利用率低
- *完全交给用户自定义*:把排序难题外包给用户,大多数用户不会配置,默认序仍然要有人负责——自定义可以作为补充,不能作为答案

【配图 4:排序前后对比图,标注三因子如何作用于具体功能】

### 决策 B|准入与去向:什么配进控制中心

产品侧定义的新功能持续到来,我为控制中心建立了一条准入判断:

> **控制中心只收"驾驶中会用、状态会变、操作是一步开关或一步调档"的功能;需要浏览、需要多步配置的,沉设置页。**

三个例子【需素材:替换为真实功能】:

- 【功能 X】:驾驶中高频、一步开关 → 一级常驻
- 【功能 Y】:低频但状态需要被看见 → 一级不给常驻位,收进展开面板
- 【功能 Z】:配置型、多步操作 → 沉设置页,控制中心不给入口

这条规则把"产品让加"转写成了"我定义了进入方式与呈现层级"——需求来源是产品的,**功能落在哪一层、以什么形态出现,是设计侧的裁量权,而我建立了行使这个裁量权的规则。**

【配图 5:准入决策树(一图讲清什么进、进到哪)】

【需校准:三个约束哪个你真的处理过,处理过的展开写实例,其余降级为一句"遵循的通用约束"】

## 6. ✨ LLM 延伸:当 Agent 能听懂"我有点冷",控制中心还剩什么?(2 页)

> 本节是概念推演,不是已实施项目;它与我的作品集案例②(LLM 座舱 Agent 重设计)直接衔接。

### 6.1 问题

上面的全部工作有一个隐含前提:**用户自己动手操作**。排序、热区、准入,都是在优化"人找开关"的效率。

但 LLM 驱动的座舱 Agent 正在改变这个前提。当用户说"我有点冷",Agent 直接调高温度、关掉吹面出风——不需要任何人找任何开关。那么,为"人找开关"而生的控制中心,是否就该消失?

### 6.2 判断:不是消失,而是转型——从操作入口变成 Agent 行为的可见层

Agent 接管执行后,控制中心的新职责恰恰是 Agent 无法自我提供的:

1. **执行回显**——Agent 刚才调了什么?温度从几度到几度?动作要被看见,信任才有依据
2. **当前状态**——语音是瞬时的,状态需要一个常驻的、可一眼读取的真相之源
3. **一键撤销**——Agent 理解错了("我有点冷"其实是想关空调不是升温),撤销必须比重新对话快
4. **授权开关**——哪些操作 Agent 可以直接做、哪些要先问我:授权边界需要一个用户可控的物理落点

**手动面板成为人对 Agent 的信任兜底。** 有趣的对称是:第 4 节的排序逻辑此时依然成立,只是排序对象变了——从"用户最常操作的功能"变成"用户最需要看见和干预的 Agent 行为"。高频被 Agent 代办的操作,其回显和撤销入口反而要排最前。

【配图 7:概念稿——控制中心作为 Agent 行为可见层(回显流 + 撤销 + 授权开关)】

### 6.3 通往案例②

这层"可见层"回答的是**呈现**;更难的问题是 Agent 的授权边界本身怎么设计——什么该问、什么可直接做、错了怎么降级。这是我的案例②用一个完整的重设计和可运行 demo 来回答的问题。

> 三个案例的关系:**① 我做过 Agent 要操作的工具层 → ② 我设计了操作它的 Agent → ④ 我在平台规范约束下落过地。**
