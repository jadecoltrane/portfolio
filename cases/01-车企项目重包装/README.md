## 框架

### 1. 背景与我的角色
- 量产车机控制中心的改版迭代与新功能承接;我负责交互设计,主导功能排序与布局
- 角色话术:"加什么功能是产品定义的,**怎么进、放在哪、怎么呈现是我定的**"
- 只写项目中的真实角色与决策范围：“作为 UX 设计师深度参与”；不在公开案例中加入与设计证据无关的雇佣关系信息

### 2. 发现问题
- 结构性矛盾:新功能持续加入 → 一级入口膨胀 → 驾驶中找不到 / 够不着
- 用真实用户反馈锚定问题(脱敏引用)

### 3. 复盘性竞品对照（压缩为 1 页）
- 项目当时的输入只写真实做过的布局对比
- 当前基于公开界面补做五维对照，用来检验方案放到行业参照系中是否仍然成立：入口密度 / 常驻与可自定义 / 状态可读性 / 驾驶中热区可达性 / 与设置页的层级分工
- 所有截图记录车型、版本、来源和获取日期；不把复盘结论倒写成当年的设计依据

### 4. 设计决策点(2-3 个)
- **决策 A|排序逻辑**:使用频率 × 驾驶安全相关性 × 热区可达性;附"考虑过但放弃"的替代方案(如按功能类别分组、为什么不如按频率)
  ⚠️ 重构出的依据必须是面试被追问时真能顺着讲的,不能是装出来的
- **决策 B|准入与去向**:什么功能配进控制中心、什么沉到设置页——把"产品让加"转写成"我定义了进入方式与呈现层级"
- **决策 C|车规约束**:盲操 / 瞥视、亮暗态、可达热区,专门一小节(加分叙事)

### 5. 结果：从界面结果转向规则结果
- **交付结果**：方案是否通过评审、随哪个阶段上线
- **复用结果**：固定区 / 可编辑区、默认序和容量规则是否被后续版本继续采用
- **承接结果**：后续新功能是否能在不重做整体架构的前提下进入控制中心
- **体验证据**：可引用的上线后反馈；若没有，不用模糊评价替代
- 以上只写可核实事实；无法公开的数据改用脱敏、定性证据，不编造指标

### 6. LLM 延伸（1 页，直接接案例②）
- 核心问题:**"当 Agent 能听懂'我有点冷'时,控制中心还剩什么?"**

  执行回显(Agent 调了什么)/ 当前状态 / 一键撤销 / 授权开关
  手动面板成为人对 Agent 的信任兜底
- 只保留 1 张概念图和 1 个判断：控制中心从操作入口转为 Agent 行为的可见层
- 授权规则、失败降级和完整交互流程全部留给案例②展开
