## 1. 为什么重设计：旧框架装不下新能力（2 页）

### 1.1 现有助手的问题不是"笨",是框架错了

传统车载语音的交互契约是：用户说出**接近指令格式**的话 → 系统匹配意图 → 执行或播报失败。这个契约下，系统 UI 主要围绕“匹配成功/失败”二值状态设计。

LLM Agent 打破了契约的两端：输入端，用户可以说“我有点冷”“找个能带狗进的餐厅”这类**没有标准答案的话**；执行端，Agent 可以规划多步操作、调用多个工具、甚至主动建议。但从公开实测看，已接入大模型的头部产品同样在公开场合出现“答应了却不执行、执行无反馈”的失败（车展演讲车辆无响应、直播中语音开后备箱无反应，公开报道 2026-05）——理解范围扩大了，执行过程、授权理由和失败恢复的可见性并没有跟上。

### 1.2 失败案例取证

|---|---|---|---|---|

### 1.3 问题定义

> **当座舱助手从"命令执行器"变成"有能力但会出错的 Agent",交互设计要回答的不再是"怎么让用户学会说对的话",而是"怎么让人和一个不完全可靠的智能体在驾驶场景下安全地协作"。**

因此，本案例不把五个 AI 议题平铺成知识点，而是将其组织成一个端到端的**安全委托闭环**：

> 理解用户目标 → 提出可见计划 → 判断能否授权 → 执行并同步状态 → 失败后恢复或退回手动

## 2. 安全委托闭环（8 页，核心章节）

### 阶段一｜理解：系统还缺什么信息？（1–2 页）

**原则：不把模型自报置信度直接当作正确率；用可观察的意图歧义决定交互形态。** 用户不需要知道“模型说自己有 78% 把握”，需要知道系统还缺什么信息、是否会立即执行。

意图歧义由以下信号构成：必要参数缺失、指代不明、多个工具同时匹配、用户表达与车辆状态冲突。系统据此切换三种形态：

| 意图状态 | 交互形态 | 例 |
|---------|---------|---|
| 信息完整、动作低风险 | 进入策略层判断 | “我有点冷”→ 候选动作：升高主驾温度 |
| 存在一个关键歧义 | 复述理解并询问必要信息 | “导航去公司”→“是常用地址还是最近一次地址？” |
| 多个意图并列 | 给 2–3 个候选，不猜测执行 | “关掉它”→“空调、音乐还是车窗？” |

关键设计点:
- **歧义不是报错**：换一种问法，不制造“你说错了”的失败感。
- **驾驶中候选上限 2–3 个**：语音与屏显同步编号，避免长列表。
- **风险优先于流畅**：即使意图信息完整，高风险动作仍需进入策略层拦截。

【配图 2：三种意图状态 + 一个从歧义到澄清的完整流转】

### 阶段二｜提案：把规划与等待变成可理解状态（1–2 页）

**原则：流式是技术事实，不是必须暴露给用户的交互形态。** 驾驶场景下，逐字滚动会产生不可瞥视的半句话；用户更需要知道系统正在做什么、下一步会发生什么。

- **先给接受反馈**：立即说明“我来查找同时满足充电和遛狗条件的地点”，不让用户猜系统有没有听见。
- **语音按句播报**：攒成一个语义完整的句子再开口；首个可理解反馈时间作为 Demo 验证指标，而不是先写死未经测试的 1.5 秒目标。
- **屏显按块更新**：一个步骤、一张结果卡片整体出现，不逐字滚动。
- **等待可解释**：用“正在查充电设施”“正在核对周边条件”等行为说明替代抽象转圈。
- **允许打断**：用户可随时停止播报；系统保留已经明确的目标与参数。

【配图 3:双通道时序图(生成流 vs 语音播报 vs 屏显更新)】

### 阶段三｜授权：由策略层决定能不能做（3 页，与案例①咬合）

**原则：LLM 只提出候选动作，确定性的策略层决定能否执行。** 策略层综合四类输入：

1. **动作风险**：可逆性、安全后果、是否涉钱或隐私、是否影响第三方。
2. **车辆状态**：P/D 挡、速度区间及当前驾驶任务。
3. **用户授权**：用户允许自动执行、每次确认或禁止的范围。
4. **意图歧义**：必要参数是否齐全、是否存在多个合理解释。

策略层输出四种结果：

| 结果 | 判据 | 例 | 交互 |
|------|------|---|------|
| 直接执行 | 低影响、可逆、状态允许且不超过用户授权 | 调温、音量 | 执行 + 回显 + 一键撤销 |
| 请求确认 | 意图明确，但会显著改变行程或影响他人 | 导航改道、发送消息 | 复述对象与后果后确认 |
| 停车后继续 | 操作复杂、涉钱或在行驶中不适合完成 | 预约付款、长列表比较 | 保存任务，P 挡恢复 |
| 拒绝执行 | 当前状态下存在不可接受的安全风险，或用户明确禁止 | 高速状态下的高风险车控 | 说明原因 + 提供安全替代 |

现实锚点：2026-02 多品牌被曝“行驶中语音误关大灯”缺陷（其一酿成实际碰撞），厂商紧急补丁的规则——行驶中禁止语音关闭外灯、仅 P 挡且指令明确时允许——正是“动作风险×车辆状态”判据的现实版。**策略层不是过度设计，是事故已经替行业验证过的必需品。**

关键设计点:
- **边界可感知**：授权设置页按动作类别显示当前规则和车辆状态限制。
- **边界可调整**：用户可以收紧授权；系统安全底线不可被用户降级。
- **边界可解释**：拦截时说明决定它的关键条件，例如“行驶中暂不支持付款”。
- **边界可追溯**：行为记录包含请求、策略决定、执行结果与可撤销状态。
- **与案例①咬合**：控制中心成为 Agent 行为的可见层——回显、撤销与授权状态的常驻落点。

【配图 4：策略层输入/输出图 + 授权设置界面 + 行为记录】

### 阶段四｜执行：让动作与状态同步可见（1–2 页）

**原则：通道分工服从驾驶注意力预算。** 以 NHTSA 视觉—手动任务指南中“单次离路视线不超过 2 秒、任务累计不超过 12 秒”的测试标准作为验证参考，而不是把它误写成每个界面天然合规的结论。

- **语音**：播报结论、关键后果与确认问题，不朗读细节列表。
- **中控屏**：显示完整可读的状态卡和 2–3 个候选；D 挡不出现需要滚动或连续点按的任务。
- **HUD（若有）**：仅承载导航、执行结果等即时信息，不作为复杂授权入口。
- **停车态**：P 挡恢复长列表、完整比较和付款等高负荷任务。
- **状态同步**：语音回显、中控卡片和模拟车控状态必须指向同一个真相之源。
- **主动发言节制**：行驶中只主动播报安全相关和用户明确订阅的事项，其余进入稍后摘要。

【配图 5:通道分配矩阵 + 行车/停车两态对比】

### 阶段五｜恢复：失败之后仍有下一步（1–2 页）

**原则:每种失败都有明确的"下一步",用户永远不会站在死胡同里。**

| 失败类型 | 系统行为 | 用户的下一步 |
|---------|---------|-------------|
| 网络断 | 显式声明 + 降级到本地指令集(车控/媒体本地可用) | 常用车控不受影响 |
| 意图歧义/听错 | 转确认式，指出缺失信息 | 选候选、补参数或重说 |
| 幻觉风险(事实类回答) | 事实类信息标注来源;查不到就说查不到 | 不被错误信息误导 |
| 执行失败 | 回显失败原因 + 保留意图上下文 | "重试/换方式/算了"三选一 |
| 当前状态不允许 | 保存任务并说明恢复条件 | 停车后继续或取消 |
| 用户失去耐心 | 停止播报并回到手动入口 | 不要求重新完成整轮对话 |

**手动兜底是安全网，也是信任机制**：用户知道随时能收回控制权，才敢把控制权交出去。这一点由设计原则自检表与案例①的行为可见层共同支撑。

## 3. 关键场景走查（2–3 页）

三个场景不是演示脚本，而是**策略层出口的覆盖测试**。每一步的判断都能在 Demo 里原样复现，判据来自工具元数据与车辆状态，不是逐场景写死的分支。

### 场景一｜“我有点冷”——最短闭环（3 关键帧）

夜间行驶，D 挡 60km/h。

| 阶段 | 系统行为 |
|------|---------|
| 理解 | 参数无缺失、无并列候选 → 不澄清，直接进策略层。目标温度由当前 22°C 推出 24°C |
| 提案 | 语音先给接受反馈：“听到了，你觉得冷。我把空调从 22°C 调到 24°C。” |
| 授权 | 空调类：低安全影响 × 可逆 × 影响范围仅座舱 × D 挡允许 × 用户授权为自动 → **直接执行** |
| 执行 | 中控状态卡 `22°C → 24°C`，与车辆状态同一真相之源；语音不再复述细节 |
| 恢复 | 卡片常驻一键撤销，撤销后状态卡回到 22°C |

**这一场景要证明的是节制**：低风险动作不该被确认弹窗打断。安全设计的价值不在“拦得多”，而在拦得准。

> **面试官可以试**：把授权设置里的空调改为“每次确认”，同一句话立刻变成请求确认——**边界可调整，且用户能收紧**。

【配图 7：场景一关键帧 ×3（接受反馈 / 执行回显 / 撤销）】

### 场景二｜“找个能充电还能遛狗的地方”——提案与等待（4 关键帧）

复合条件、多步任务，考验的是等待过程能不能被理解。

| 阶段 | 系统行为 |
|------|---------|
| 理解 | 两个条件都明确，无需澄清 |
| 提案 | 立即接受反馈 + 亮出三步计划：查附近充电站 → 筛选宠物友好/绿地条件 → 按顺路程度排序。等待期用“正在核对周边遛狗条件”这类行为说明替代抽象转圈 |
| 授权 | 地点检索为**只读查询**，不改变车辆状态 → 授权允许即执行。风险判据看的是“会不会改变状态”，不是“是不是云端功能” |
| 执行 | D 挡：语音播报 2–3 个候选并编号，屏显整块出现结果卡；P 挡：恢复完整列表与横向比较 |
| 恢复 | 若此时断网：只读检索依赖云端 → **显式声明降级**，而不是转圈到超时；同一时刻说“我有点冷”仍然执行，本地车控不受影响 |

选中候选后进入“预约充电桩”，剧情自然转向场景三。

**这一场景要证明的是：流式是技术事实，不是必须暴露给用户的交互形态。** 驾驶中用户需要的不是逐字滚动，是知道系统在做什么、下一步会发生什么。

【配图 8：场景二关键帧 ×4（接受反馈+计划 / 等待行为说明 / D 挡候选 / 断网降级）】

### 场景三｜行驶中改行程、预约付款、途中断网——拦截与恢复（5 关键帧）

同一段行程里连续触发四类拦截，用来说明策略层是一套统一判据，不是四个特例。

| 用户说 | 策略层判据 | 输出 | 用户看到的下一步 |
|-------|-----------|------|----------------|
| “导航去公司” | 存在两个合理解释（常用地址 / 最近一次地址） | **需要澄清** | 复述理解并二选一，不猜测执行 |
| （澄清后确认目的地） | 导航改道显著改变行程 | **请求确认** | 复述目的地与后果后确认，执行后可撤销回原路线 |
| “预约这个充电桩” | 涉钱 × 不可逆 × 仅 P 挡允许 × 行驶中属高负荷任务 | **停车后继续** | 任务存入待办，不弹更强的窗逼用户在 60km/h 下付款 |
| “关掉大灯” | 高安全影响 × 非 P 挡 | **拒绝执行** | 说明原因 + 给替代：停车挂 P 后可执行，或用物理开关 |
| “关掉阅读灯” | 同属灯光类，但低安全影响 × D 挡允许 | **直接执行** | 证明拦截的是**风险**，不是灯光这个类别 |
| （途中断网） | 云端工具不可用 | **断网降级** | 显式声明 + 本地车控照常 |
| （挂入 P 挡） | 恢复条件满足 | 待办任务恢复 | 停车后继续完成预约付款 |

**这一场景要证明的是安全底线不可协商。** 把灯光授权调到“自动”，行驶中关大灯依然被拦——用户可以收紧授权，但不能把系统的安全底线降级。这条规则的现实锚点就是 §2 阶段三写的 2026-02 行业事故。

## 5. 局限与验证计划(1 页)

如实写,这是 HCI 训练的体现:

- Demo 使用模拟车控 API，没有真实车机延迟、CAN 总线和量产功能安全约束。
- 当前验证只覆盖脚本化机制测试：策略结果一致性、失败恢复、行驶/停车两态、首个可理解反馈时间和状态同步。
- 没有真实道路环境的分心测评；若进入落地阶段，再使用驾驶模拟器、瞥视时长测量和 NASA-TLX 等方法。
- 授权规则仍需通过真实用户研究和安全、法务、工程评审校准；“影响大”并非完全由设计师单方面定义。
- 本项目的边界是“把问题定义清楚并给出可检验答案”，不是量产方案或安全认证。
