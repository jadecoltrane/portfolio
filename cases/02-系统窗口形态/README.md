### 1. 背景与我的角色
一块车机屏要同时承载全屏应用、小窗、无界应用、Dock，形态越加越多。写清楚我负责哪一层。

### 2. 问题：形态增加带来的结构性冲突
不是"不好看"，是**系统没有统一的仲裁规则**：两个小窗同时想出现怎么办、无界应用能不能压住 Dock、编辑态下其他形态怎么处理。

### 3. 形态定义：先划边界再谈规则
全屏 / 小窗 / 无界应用 / Dock 各自的职责、尺寸约束、可停留时长、能否被驾驶态打断。

### 4. 决策点（2–3 个，本案例的核心）
- **决策 A｜层级与压盖**：谁在上谁在下，依据是什么
- **决策 B｜打断与让位**：什么情况下一个形态必须让位（与案例⑤事件仲裁、案例①驾驶安全约束呼应）
- **决策 C｜进入与退出**：怎么被拉起、怎么收回、结束后谁负责收尾
- 每个决策都要有"考虑过但放弃"的替代方案

### 5. 规范化：从个案判断到团队可执行的规则
这一节是与案例①《控件规范审查》呼应的地方——证明我的产出不止是稿子，是**别人能照着执行的规则**。

### 6. 结果与复用
上线情况、规则沿用情况、后续新形态是否能在不重做架构的前提下接入。
